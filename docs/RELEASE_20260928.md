## Despliegue supervisado

Tras publicar el commit aprobado en `main`, y solo con respaldo confirmado:

```bash
sudo -u lyn git -C /opt/lyn status --short
sudo -u lyn git -C /opt/lyn rev-parse HEAD
sudo -u lyn git -C /opt/lyn fetch origin
sudo -u lyn git -C /opt/lyn pull --ff-only origin main
sudo -u lyn git -C /opt/lyn rev-parse HEAD
```

Detenerse si hay cambios locales de archivos versionados, falla el fast-forward o el SHA no coincide con el aprobado. No usar `reset --hard` para descartarlos. No seguir pegando comandos mientras una compilación sigue ejecutándose.

```bash
sudo bash /opt/lyn/deploy/scripts/preflight.sh
sudo bash /opt/lyn/deploy/scripts/deploy.sh
```

El script compila, migra y reinicia servicios; espera `/ready` antes de publicar el dashboard y conserva assets anteriores. Las migraciones no se revierten automáticamente. Vigilar memoria y disco: el servidor reportó aproximadamente 909 MiB de RAM y 2 GiB de swap; no ejecutar compilaciones concurrentes. Un proceso terminado por falta de memoria no es un despliegue satisfactorio.

## Reversión

Ante un fallo, detener la publicación y preservar logs. Para un problema solo de frontend, restaurar el frontend respaldado compatible con el backend. Para volver al código anterior, usar el SHA registrado y su versión compatible de las dependencias; no lanzar migraciones antiguas contra una base nueva sin verificar compatibilidad.

Si se requiere restaurar una base, detener escrituras/servicios afectados, guardar también el estado fallido y restaurar el respaldo con supervisión. Esto puede perder cambios posteriores al respaldo; requiere aceptación expresa. No ejecutar restauraciones destructivas de forma automática.

No se exige ensayo Linux separado por decisión del usuario. Esto no demuestra compatibilidad en el servidor real ni sustituye el control posterior al despliegue. No se garantiza ausencia universal de bugs.
